# 聊天 Gateway 多节点与共享会话实施计划

状态：2026-10-05 本批代码、357项全模块回归与八组真实Boot网络行为通过，未发布。
上一批 V4 真实 SQL/双 JVM 证据不能替代本批真实登录/发现验证。
失败轮次/实际产物/清理与剩余门槛见[完整网络记录](CHAT_GATEWAY_NETWORK_VERIFICATION_20261005.md)。
沿用[企业路线](ENTERPRISE_ROADMAP.md)，保留全部阶段门槛，不改变上线定义。

## 不变量

- Gateway 先验证共享会话并删除伪造可信头，下游 WS 握手和每次 SEND/PING 继续检查会话。
- HTTP 注册端口不是 Netty WS 端口；WS 路由选到哪个聊天实例，就使用该实例的 WS 元数据。
  不能先选择 HTTP 实例，再固定连接另一节点；不另建本机随机分流表。
- 元数据缺失/不规范、错误服务或发现不可用须失败关闭；不退回 HTTP 端口或任意外部 URI。
- 定址 `ws://` 入口保持兼容；`lb:ws://koko-nexus-chat` 需明确配置后启用，不能自动开启生产扩容。
- 会话注销后，两节点拒绝该令牌；Redis 故障不放行发送，不把服务不可用报成成功。
- 外部依赖和测试用户只放隔离环境；不重启生产注册中心/缓存，不恢复 AI 短剧。

## 开发与验证顺序

1. Nacos HTTP 注册增加节点 WS 端口元数据；Gateway 在真实 ReactiveLoadBalancer 选择后
   仅替换同一实例的目标端口。格式、范围、协议、路径编码及固定路由兼容测试。
2. 冻结本轮可执行 JAR；独立注册中心/Redis/限权 MySQL，启动 Gateway、身份及双聊天 Boot。
3. 经真实注册/登录/HTTP/WS 验证发现分组、伪造头、定向同步、历史/移除/重入、
   注销/撤销、Redis 故障关闭与恢复、节点退出与新连接。
4. 有浏览器条件时完成双端聊天接收/错误/恢复 UI；未执行则单独保留门槛。
5. 先备份合成库与证据，再定向清理并核验；更新文档，不把局部网络通过当容量或公网验收。

## 发布前置

先升级所有 chat 实例并确认正确 WS 元数据/监听地址，才切 Gateway 到发现 WS 路由；
禁止在仍有旧无元数据节点时启用。生产仍用单节点定址入口，需独立备份/滚动发布/公网验收。
TLS、全局连接配额、慢客户端长压、告警接收人、媒体 RTC 和正式上线签字仍保留。

依据项目实际 Spring Cloud Gateway 4.3.0 源码及
[官方 WebSocket/负载均衡说明](https://docs.spring.io/spring-cloud-gateway/reference/4.2/spring-cloud-gateway/global-filters.html)。
`lb:ws` 只解决发现/选择，不自动知道自定义 Netty 监听端口，也不完成共享身份与客户端重连。
