# Netty 聊天闭环实施与验收

## 范围和不变量

Java 主导的 chat-service 独立数据库，Nacos 注册，Dubbo 查询身份，Gateway 鉴权；Netty WebSocket 推送与收发，MyBatis-Plus / XML 持久化。LiveKit 继续负责音视频，不承载聊天事实。

- 私信按排序后的用户对唯一；群聊最多 50 人，仅群主增删成员、改名或解散，普通成员可以退出。
- 会话行锁串行化消息序号及成员变更；数据库提交后才返回 ACK。同一用户、会话、客户端 UUID 重试返回原消息，不同正文返回冲突。
- 群成员加入前的消息不可读，移除后不能读写。已读游标只前进且不超过已存在消息。
- 网关删除伪造身份头，下游校验内部密钥；WebSocket 限定 Origin，握手及每次消息/心跳重新验证共享 Sa-Token 会话。退出登录后的旧连接不能继续发送。
- JDBC、Dubbo、Redis 不在 Netty EventLoop 执行；业务线程、任务队列、帧大小、连接数、心跳和慢客户端都有上限。
- 实时推送是尽力而为，不宣称零丢失或恰好一次。消息事实在 MySQL，前端重连/定期刷新按游标恢复；部署初期只允许一个聊天实例，扩容前实现跨节点分发。

## 2026-10-01 阶段验收证据

最新后端全模块 103 项测试通过，无失败/错误/跳过；前端 Vue TypeScript 和生产构建通过。独立真实 MySQL 验收验证了 24 路并发发送的连续序号、幂等重试与冲突回滚、成员历史边界、已读不回退和解散后保留记录，临时库及测试用户已清理。

公开 Nginx → Gateway → Netty → MySQL/Redis 链路以真实合成账号通过 56 项断言：私信用户对唯一、正文持久化、重试不重复、伪造身份不生效、错误 Origin 拒绝、离线消息补拉、群主权限、入群前历史不可见、移除后读写拒绝、七组 OpenAPI/Knife4j 资源及注销后旧连接失效。随后重启聊天 JVM，再确认两条私信仍可查询且公开握手返回 101。最后部署包与源码核对 SHA-256，不能以模拟测试代替上述结果。

Java 注释审计 `scripts/java-contract-docs.mjs` 输出无待补项；前端业务契约审计 `scripts/frontend-contract-docs.mjs` 输出无待补项。字段说明覆盖标识精度、单位、状态、可空性、敏感信息和幂等语义；Lombok 实体只生成访问器，不自动生成敏感 toString。

## 发布约束

当前服务器只有约 3.6 GiB 物理内存，交换区不是性能保障；先验证新增 JVM 容量，不重启共享中间件或旧项目。HTTP 公网仍缺 TLS，生产凭据与消息必须迁移 HTTPS/WSS 后才能正式开放。新增 schema 必须先备份，禁止删除或重写已有迁移。
