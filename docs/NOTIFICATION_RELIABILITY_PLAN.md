# 通知可靠性隔离演练计划

阶段 2 仍有死信人工重放/审计、外部告警、恢复/容量门槛。本轮不将其缩小成已完成阶段；先补真实 Broker 中断和消费恢复证据，再按路线继续交付剩余功能。

## 不变量与隔离

- 关注关系、粉丝计数和 Outbox 由实际 identity 用例、MP/XML、Spring 代理同事务写入；Broker 不可用不改变已提交业务结果。
- 实际生产 RocketMqEventSender/OutboxRelay 与 NotificationApplicationService/RocketMqNotificationConsumer 参与演练，不用假发送或手写替代消费者证明生产逻辑。
- 发送成功但 SENT SQL 失败允许重复；收件箱/处理回执只出现一次，不覆盖已读。消费 SQL 失败回滚回执，并由真实 Broker 重投，而非测试直接再次调用 deliver。
- 偏好抑制形成持久回执，重复消息不反复展示；重试有上限，不把 Broker ACK 等同业务成功。
- 专用内部 Docker 网络、NameServer/Broker/消费组/主题、限权命名测试库和一次性 Java 进程；不映射公网，不注册生产 Nacos，不停生产 Broker，不接触生产事件。
- 仅已创建且标签/ID 匹配的资源可停止/删除，拒绝覆盖既有容器/网络/库；先保存隔离库与日志证据后清理。服务器内存/磁盘前置检查和在途资源保护，不以 swap 代替容量测试。

- [x] 真实生产类编译，既有回归测试；本轮不改 Web 契约，不强造无关前端改动。
- [x] Broker 运行时基线关注 → SENT → 1 通知；本人已读和他人拒绝。
