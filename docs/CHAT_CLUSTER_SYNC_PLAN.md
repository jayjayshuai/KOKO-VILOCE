# 聊天跨节点同步实施计划

状态：2026-10-05 本批源码/自动回归/真实隔离 SQL 与双 JVM 验证通过，未发布。
依据语音 P0 的跨节点前置要求；不替代麦位事件总线。
范围、失败记录与未通过门槛见[验证记录](CHAT_CLUSTER_SYNC_VERIFICATION_20261005.md)。

## 不变量

- 消息、成员、群名、解散及同步版本在同一个 MySQL 事务提交；版本写失败，业务整事务回滚。
- 每名受影响用户一条持久版本记录，不保存消息正文或设备令牌。按用户 ID 升序写锁，
  业务锁之后才写版本，避免不同会话反向更新同一批用户造成版本锁死锁。
- 幂等消息重试不重复增加版本；移除成员必须通知被移除人及剩余成员。
- 会话锁后的成员授权/收件人/群上限使用当前读，不复用外层预先建立的 RR 快照。
  用另一个真实连接提交加人/踢人验证；否则锁了会话仍可能读取旧快照成员。
- 各 Netty 节点仅轮询本节点已认证用户，分批最多 100，工作不在 EventLoop 执行。
- 只推送无正文 SYNC 提示，HTTP 补拉仍验证当前成员与入群序号；旧提示不能授予权限。
- 节点/数据库暂时不可用后重新读取持久版本；失败不推进本机观察值。
- 客户端读取中收到同步请求必须排队；切会话/卸载隔离旧结果，恢复焦点重新查事实。

## 范围与取舍

这是基于共享 MySQL 的**持久失效通知**，不是逐事件日志或恰好一次推送。
合并多个版本合法，因为现有前端按消息 UUID/序号补拉事实，而不按提示数量计数。
默认一秒轮询，最多 500 个本机网络连接；多人群消息最多 50 条版本行写放大。
不新增 JVM/Redis/MQ，不把当前资源条件或测试等同容量认证。
扩容前仍须真实双 JVM、并发/回滚、故障恢复、慢客户端、HTTP 鉴权和容量验收。
滚动升级时旧节点不会登记版本，客户端十五秒事实补拉保底；所有节点升级前不保证一秒发现。

## 公开依据

版本 upsert 检查 MySQL 实际新增/更新受影响行数，不使用 `INSERT IGNORE` 吞错误，
参考 [MySQL 8.4 upsert](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html)。
Netty 发送异步完成不证明客户端已经收到，参见
[Channel API](https://netty.io/4.1/api/io/netty/channel/Channel.html)。
