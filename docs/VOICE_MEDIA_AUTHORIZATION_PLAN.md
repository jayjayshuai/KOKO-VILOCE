# 自建LiveKit媒体授权与撤权实施

本文件扩展既有语音房P1，不缩减企业路线或宣称已完成媒体链路。
2026-10-06开始实现，现有CONTROLLED媒体准备度继续false，生产入口未变更。

## 必须解决的真实边界

[LiveKit官方令牌说明](https://docs.livekit.io/frontends/reference/tokens-grants/)明确：自建部署删除成员或修改权限
不使既有JWT失效；服务端还会刷新令牌。不能把短TTL、前端禁麦或RemoveParticipant等同即时撤权。
准入之后SQL仍可变化，信令检查不证明持续连接授权，也不自动撤销已建立的音轨。

## 原始验收目标及实施顺序

1. Java Gateway唯一公开信令入口：现有Sa-Token会话、来源白名单、JWT验签与当前房间事实；
   服务间用Dubbo，不把LiveKit管理密钥放Gateway。原始SFU 7880和公开绕过路由收为私有，
   仅保留必要ICE/TURN媒体端口。必须实际HTTP/WS/身份二跳/SQL/TLS验收后发布。
2. 持久媒体绑定与同事务撤销意图：成员session与单调media epoch形成独立不含PII的身份；
   上麦/下麦/闭麦/离房/租约过期改变授权轮次，旧轮次不能在准入处被重新认可。
   Core成员或席位事实、媒体计划、审计和收据同事务，不把外部调用放SQL行锁内。
3. 媒体执行与补偿：持久任务、有限尝试、租约/CAS确认、失败采样和运维恢复；
   旧执行不得授权新身份。评估轮次身份更换与旧身份退场，不直接用无版本的UpdateParticipant
   并声称跨节点围栏已成立。未知结果保持未确认，不签发新的发布令牌，不假装已闭麦。
4. 准入和持续连接的竞态：核验→握手期间仍有变化窗口；旧身份隔离、持续核验与旧参与者
   清退需覆盖晚到握手、进程暂停/恢复、RPC超时、重连和服务端刷新JWT。不得仅用一次HTTP核验
   声称无旧音轨。故障关闭要有实际SFU/两浏览器媒体证据和明确时限。
5. 前端真实能力接入：默认不开麦、SDK权限反馈、麦位操作等待媒体确认、身份/轮次变化定向
   断开与新凭据恢复、拒绝回填旧JOIN/JWT。媒体实际发声与SQL希望值分别显示。

## 本轮候选边界

实现第1项的Java准入源码与受限路由，固定HS256/发行方/身份/房间/语音源核验，
当前Active身份二跳在SQL事务外，房间当前锁拒绝CLOSING/CLOSED或CONTROLLED旧凭据。
默认两端开关false；新令牌明确禁数据发布和自改元信息，文本聊天仍通过Netty。
旧10分钟平台令牌缺data字段保留准入兼容，但不接受管理、视频/屏幕发布或跨网站身份。

本批不是第2～5项；不把候选信令代理当成麦位权限完成。
原端口/边缘入口仍兼容旧发布配置，因此未证明无法绕过。生产迁移、入口私有化、TLS、
持续授权、持久补偿、真实SQL/RTC双端与容量均须后续实证。
