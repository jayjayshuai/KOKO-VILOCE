# 聊天反骚扰与举报审核阶段

## 范围与不变量

前端与后端同步实现拉黑/解除拉黑、本人拉黑列表、消息举报、本人举报进度、受权限保护的人工审核队列。沿用 Java 微服务和现有技术栈，不新增 JVM。新增 Flyway V2，不改已部署 V1。

- 任一方拉黑后不允许建立新私信或提交新私信消息；历史仍可读取，已提交消息的原 UUID 重试仍返回原事实。拉黑与新消息提交采用共享用户对锁，拉黑返回成功后新消息不得绕过。
- 拉黑同时阻止拉黑双方之间的新群邀请；既有共同群不会被自动解散或隐藏消息。前端明确说明此边界，不将拉黑宣传为完整屏蔽。
- 每人最多 1000 个拉黑关系；本人操作串行化，重复操作幂等。对外只返回本人拉黑名单，不泄露对方拉黑设置。
- 只能举报本人当前有权读取、在入群历史边界之后的他人消息；举报快照和消息事实一致。每人每条消息最多一份，同内容重试幂等，不同内容冲突；每人滚动 24 小时最多 20 份。
- 举报人只能查询自己的举报，不能读取审核证据或其他举报人信息。审核员必须通过共享 Sa-Token 会话和权限检查；默认没有审核员，首位审核员须由用户明确指定，不能自动授权普通账号。
- 审核仅由 PENDING 转为 RESOLVED/REJECTED，要求版本号和说明；决定和不可变审核记录在同一本地事务。结案不自动封禁账号，也不等于建立全部运营 RBAC。
- 审核员初期由服务端明确配置的用户 ID 集合提供 Sa-Token 角色/权限；前端隐藏按钮不作为权限保障。未配置时真实返回无权限。

## 边界

HTTPS/WSS、真实 UI 点击、容量、完整角色管理、内容封禁、申诉与合规保留策略仍是独立上线门槛。若未得到审核员身份，不擅自赋予任何生产用户审核权限；只在隔离测试环境验证正向审核流程，并在交付中标明公开正向审核未验收。
